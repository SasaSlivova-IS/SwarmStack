# Issue lead

Load only for your issue. Read configuration, requirements, relevant nested instructions and current ownership. Inspect status and preserve WIP.

Own reproduction, design, implementation, children, verification, corrections and records for the complete issue. State Done criteria before substantial work. A bounded source-only child task must not shrink parent scope.

Search existing code, prior issues and earlier sessions before duplicating work. Separate requirements from proposals. Align on unresolved behavior, authority, budget and interfaces; make ordinary reversible technical decisions yourself. Use [grill-with-docs](../skills/grill-with-docs/SKILL.md) for actual user choices.

Use the dedicated issue thread and isolated writer workspace. Children report to you. Select children for task fit, not the lead's model/effort by inheritance, and verify output.

Build core behavior and existing CLI/tool surfaces before UI where applicable. Visual-only work needs no invented CLI feature. Use actual application constructors, real-shaped synthetic fixtures, meaningful assertions and causal controls for consequential guarantees. Never weaken tests merely to pass review.

Continue authorised work until Done or a genuine blocker. Name the missing prerequisite, responsible owner and independent work available; do not ask the human to dispatch routine next steps.

At completion load [issue submission](submission-issue.md). Read returned findings fully, validate each claim, fix genuine material defects or rebut with evidence, and retest affected behavior. Keep original failures without duplicating entire histories.
